## Description

EmployeeAvailability guardrails. Employees currently self-serve their
unavailability (`EmployeeAvailability` + weekly `UnavailabilityBlock` value
objects) with no timing rule and no fairness rule, creating two concrete risks:
(1) last-minute unavailabilities against shifts already in a published roster,
and (2) an employee blocking every peak slot (evenings + weekends) when the
restaurant needs capacity most.

This initiative adds automatic, transparent guardrails enforced at write time,
plus after-the-fact manager visibility. **Hard product constraint: the manager
never approves an employee unavailability — there is no approval workflow.** The
solution is rules + read-only metrics, never a human gate on the employee's
action.

## Scope

- **Notice window (timeliness):** for an employee author, `effectiveFrom >= today
  + noticeDays` (default 14, company-configurable); else 400. Manager/Admin retain
  the right to backdate.
- **Peak hours (Layer 1):** reuse the existing `OperationalSettings.peakHours`
  (manager-defined, time-ranged). No new `RestaurantPeakHours` concept.
- **Hard peak quota (Layer 2):** an employee cannot render unavailable more than
  50% of the restaurant's peak hours; breach → 400. MVP single threshold;
  full-time/part-time differentiation deferred to v2 (policy field kept
  extensible).
- **Conditional justification (Layer 3):** `UnavailabilityBlock.reason` becomes
  required (min 20 chars) when the block intersects peak hours.
- **Proactive alert + dashboard (Layer 4):** new async event
  `EmployeeAvailability.PeakThresholdReached` at a configurable alert threshold
  (default 40%) → manager notification; new read-only endpoint
  `GET /restaurants/{id}/availability-metrics` (per-employee peak-unavailability %,
  weekday distribution, aggregated reasons, headline counts, and trends over time).
- **Policy aggregate:** new `CompanyAvailabilityPolicy` (company-scoped, mirrors
  `TimeOffPolicy`) holding `noticeDays` (14), `peakQuotaPercent` (50),
  `alertThresholdPercent` (40), `justificationMinChars` (20); validate
  `alertThresholdPercent < peakQuotaPercent`.

## Out of scope

- Any manager approval / reject / pending workflow on employee availability.
- Full-time/part-time or contracted-hours differentiation of the quota — needs a
  new Employee-domain concept (`employmentType`/`EmploymentTerms`); v2.
- Creating a new `RestaurantPeakHours` concept — reuse `OperationalSettings.peakHours`.
- Changing roster generation — this only reads roster state for the timeliness rule.
- Time-off (`TimeOffRequest`) — a separate, already-approved-flow domain.
